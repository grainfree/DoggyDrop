# Administrator bootstrap security hotfix

Baseline: `5984c241464056d7a749d09f570317b7e1aafa1a`.

## Previous behavior and exposure

The previous startup path ran after database initialization in every environment. It created the Admin role if absent, then created an account for a fixed email with a committed literal password if that email did not exist. It attempted to add the newly created account to Admin. Identity operation results were not checked. It did not reset an existing password or grant an existing ordinary account the role. Unhandled Identity/database failures could still prevent startup.

The exposed credential is intentionally not reproduced here or in regression tests. Removing it from current source does **not** remove it from Git history or change any existing account. History has not been rewritten. Production validity has not been tested.

**Owner action:** use a trusted, owner-controlled account-management process to review accounts that could have been initialized by this path, replace any potentially affected password with a new unique credential, and revoke affected sessions as appropriate. Do not reuse the exposed credential for bootstrap. This code does not perform password rotation, session revocation or production account inspection. Code remediation alone does not establish that a real account is safe.

## Explicit initial setup

Configuration keys (names only):

- `AdminBootstrap:Email` / environment variable `AdminBootstrap__Email`
- `AdminBootstrap:Password` / environment variable `AdminBootstrap__Password`

Supply these through the deployment platform's protected environment/secret configuration only when initial administrator creation is required. For local Development, use user-secrets or local environment configuration. Do not put values in tracked appsettings, examples, shell history, documentation or logs. Choose a long, unique password generated by a password manager. Bootstrap requires at least 12 characters and all existing Identity password validators; it does not alter global password policy.

The same rules apply in Development, Test and Production:

1. Ensure the Admin role exists independently of a password.
2. If any account already has Admin membership, skip credential bootstrap without requiring or validating bootstrap values. Passwords, security stamps and memberships remain unchanged.
3. If no Admin exists and both settings are absent/blank, commit role creation, emit a value-free warning and continue startup with no administrator account. Public functionality may start; Admin endpoints remain authorization-protected. There is no default password.
4. If no Admin exists and configuration is partial, malformed, too weak, or conflicts with an existing account, fail startup with a fixed, value-free error. An ordinary account is never promoted implicitly. Existing-account recovery/role assignment requires an explicit owner-controlled operation.
5. With valid explicit configuration and no existing account conflict, create the initial account with its email confirmed and grant Admin atomically. Check every Identity result. A failed creation or role grant rolls back the transaction. Never reset a password.

PostgreSQL uses a dedicated transaction advisory lock `(194721, 23001)` to serialize competing bootstrap instances. Database changes, including the eligibility check and role grant, share a transaction. No schema change is required. This does not implement an ongoing administrator-management service.

After successful initial setup, remove the bootstrap password setting from the deployment configuration; a restart with an existing Admin does not need it. Do not delete an existing account to trigger bootstrap or expect bootstrap to repair lost access.

Logs describe only created/already-existing/skipped outcomes. No email, password, hash, configuration object or secret value is logged by the bootstrap. Failure messages do not propagate Identity validator descriptions or provider exception details/inner exceptions. If setup fails, privately verify the key names, account conflict, configured password requirements and database availability.

## Related seeding and scope

`DbInitializer` seeds infrastructure only. The separate, opt-in `SeedTestUser` path already reads credentials from configuration, creates no Admin membership and does not reset existing accounts; it is unchanged. Database migration/startup behavior is also unchanged. No onboarding, PWA, SEO, security-header or other Epic 23.0 implementation is included.

The tracked-content audit found the exposed credential only in the removed startup block. Other reviewed matches were empty configuration fields, configuration-key references, documented placeholders or isolated synthetic test values. No additional credible production-capable committed credential was identified. This is a current tracked-content audit, not a guarantee about historical commits or deployment configuration; user-secrets and production environment values were not inspected.

`AdminBootstrapTests` runs the actual startup helper with real Identity stores and an isolated in-memory SQLite database under Development/Test/Production host configurations. It covers missing/invalid settings, role-only creation, explicit initial creation, unchanged existing passwords, refusal to promote ordinary users, transactional failure, safe errors/logs and source-level prevention of literal application password creation. Tests use generated synthetic credentials and never reference the exposed value or its hash.
